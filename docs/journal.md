# SmallSat Avionics - Journal

The record of what's been built and how it went. Newest first, one entry per working session, oldest at the bottom. This is the rear-view mirror; the forward-looking plan lives in `roadmap.md`.

---

### 2026-07-31 - the requirement backlog cleared, and a stale doc claim caught in passing

- **`wiring.md` was wrong about the radios, and it was wrong because I made it wrong.** It said the radios and their 3.3 V buck were deferred to Phase 8; the journal entry for 2026-07-26 says both were wired that day and "everything remaining is software". The stale claim predated me, but I rewrote that intro on 07-30 and carried it forward instead of checking it against the log. **It mattered: it made radio drivers look hardware-gated when they are not**, which is exactly the kind of error that quietly reorders a plan.
- **REQ-PAL-001 stopped being an honour system.** Its verification method is "inspection", which is a thing that stops happening the moment someone is busy - the same failure REQ-VV-004's trace checker was written to end. `tools/tests/test_pal_boundary.py` now runs in `just test`: nothing under `fsw/` may include outside the standard library, `etl/`, `fsw/` and `protocol/`, and nothing may name a peripheral outside a comment.
- **Writing that check's negative cases immediately found a hole in the check itself.** `\bNVIC\b` cannot match `NVIC_EnableIRQ`, because `_` is a word character and there is no boundary there - so `RCC_APB1ENR`, `SysTick_Config` and every other underscored form, which is how these names are almost always written, all passed. The version that only ever ran against a clean tree looked like it worked. **A checker with no failing case is a claim, not a check** - second time this project has learned that from the same shape of mistake.
- **REQ-WDG-002's other half landed.** The reset cause was only ever in the console banner, and a banner scrolls away. `boot_info_t` now carries it on `MsgId::BootInfo`, offered to the executive as a cycle input on the first cycle only - so it crosses the PAL as an input rather than a side channel, which is the same discipline every sensor sample already follows.
- **That work hit a name collision worth remembering:** `IWDG` and `WWDG` are CMSIS peripheral macros (`#define IWDG ((IWDG_TypeDef *) IWDG_BASE)`), and the wire catalog compiles in the same translation unit as `stm32f446xx.h`. The X-macro expanded into a pointer cast and buried `state.hpp` in errors pointing at unrelated lines. Renamed to `WATCHDOG` and `WINDOW_WATCHDOG`, which read better anyway, with the constraint written into the header so the next catalog entry does not rediscover it.
- **REQ-TLM-005's last clause was a number on three beads.** The fault bead holds its severity colour and winks dark once per latched fault; counting the gaps keeps the colour visible most of the cycle. Inhibited faults count, because they are latched and that is what the requirement says.
- **Asking whether more beads should blink found a bug that had nothing to do with blinking.** Bead 2 read `response_active(COMMAND_LINK_LOSS)`, and `response_active` is false while a fault is inhibited - which this build does. So the bead went green on the first command ever received and stayed green for the rest of the session, however long the ground had been gone. It asks `link_lost()` directly now: suppressing a response is a decision about safing and says nothing about whether the link is up.
- **Two of the three blink ideas were declined, and the reasons are the useful part.** A sub-timeout "going quiet" blink would have blinked continuously, because nothing keeps the link alive between typed commands and so "silent but inside 5 s" is the normal bench condition - reporting on the inside of a tolerance is noise. A DOWNLINK mode blink was killed by the previous night's own change: a whole image now leaves in about a second, so it would be over before anyone looked up. **Motion is a scarce channel on a three-bead strip**, and bead 1 is already spending it on the only thing there that carries a number.
- **REQ-SNS-003 moved from planned to deferred.** It is conditional - "where redundant sources exist" - and this build has one of everything. Kept, because it is the rule a second sensor arrives under; not planned, because planned implies queued work and none of it is buildable.
- **Bench-verified in one run:** the `BOOT` frame with the right cause, the fault bead winking twice against a two-fault heartbeat, the link bead going amber-blink to green to red at the timeout, and no `WATCHDOG UNFED` across a 165-chunk 9225-byte downlink - 50% larger than the frame that exposed the watchdog bug, so the per-chunk check-in is confirmed on a case the old code would have failed.
- **The same run caught the health task drifting under the stack floor.** It reported 94 words free of 192 - 98 used, a 1.96x margin against this file's ~2.5x convention, and the tightest in the system. It grew because it now reports on seven task slots instead of five and hands its frame to the telemetry buffers rather than to a uart. Raised to 256. Worth noting the general shape: **every task that gains work needs re-measuring, and nothing prompts you to do it** - the number was sitting in every TASKS line for a day before anyone read it.
- **Phase 7 started: the plant model exists.** `fsw/sil/plant.{hpp,cpp}` - platform and wheel inertias, momentum exchange, wheel saturation, and friction as viscous plus stiction. It lives in `sil/` rather than `src/` deliberately: it is scaffolding, it must never be linkable into the flight image, and that is exactly the boundary the new PAL check enforces on `src/` and `include/`. Built as its own `sil_plant` library for the same reason.
- **Its tests check physics, not coverage.** Angular momentum is conserved to 1e-9 with friction off; the platform always turns opposite the wheel; a *constant* wheel speed exerts no torque at all, which is why the rig's demo is a transient rather than a spin; friction is monotonically dissipative over a hundred steps; and a 100 ms step gives the same answer as a hundred 1 ms ones. A plant model that quietly breaks conservation will happily prove a control law that cannot work on hardware.
- **Two tests failed first time and the model was right in both.** Both asked for full torque for a full second, and at the estimated parameters **the wheel saturates in about 0.18 s** - so the first read a platform already returned to rest, and the second found the wheel driven clean through zero to the opposite limit. **That number is the first real design constraint the model has produced:** a full-torque command is spent inside two control cycles, so a rate controller that asks for max torque saturates before it has seen its own effect. There is now a test asserting the saturation time against `j_wheel * rate_max / torque_max`, because it is the figure the control law has to be designed around.
- **The parameters are estimates and are labelled as such in the header.** Total momentum capacity works out at ~0.011 kg m^2/s, so ~3.6 rad/s of platform authority before the wheel is full - plausible, and not yet measured. `friction_static` is the one that matters most and the one `hardware.md` already documents a procedure for.
- **The SIL loop is closed, and it caught a sign error on its first run.** The control law had `tau = -k * omega`, which reads correct and is backwards: what the PAL commands is the *wheel's* torque and the platform feels the reaction, equal and opposite, so opposing the rate means spinning the wheel *with* it. The evidence was unmistakable once the physics was in the loop - friction alone had been removing 0.57 rad/s per cycle, and the first controlled cycle removed **0.011**. The controller was fighting the thing already stopping the platform.
- **No unit test would have found that, and that is the point.** A test asserting `detumble(1.0) == -k` passes happily on a law that accelerates the vehicle. The test suite is written in terms of the reaction now - "spinning forwards must produce a backwards push on the platform" - so the physics is in the assertion rather than the formula. **An open-loop test can check what a controller says; only a closed loop can check what it does.**
- **Two boundaries moved to physical units in the process, both for the same reason.** `set_wheel_torque` took q-axis millivolts, so the flight software would have had to know a specific motor's torque constant and winding resistance; it takes newton metres now and the backend converts. And the gyro reaches the executive as `body_rate_rads` rather than raw counts, because turning counts into a rate needs the ICM-20948's full-scale setting. Both are REQ-PAL-001 arguments and both were found by asking what the control law would have to know.
- **The plant is opt-in per scenario** (`plant: <rate>` in the timeline). With it off the shim behaves exactly as before, so the ten scenarios written before the model existed are untouched by it existing - which is why adding a closed loop did not mean re-verifying everything else.
- **SIL-011 grades bounds, not values.** The plant's inertias and friction are estimates, so an exact settling time would be pinning a number nobody has measured. What is asserted is that the rate converges inside the deadband and the wheel stays short of saturation - properties of the control law that hold whatever the parameters turn out to be.
- **An honest reading of the run: friction is doing most of the work at these parameters.** Uncontrolled, the platform decays from 2.0 to 0.81 rad/s in 200 ms on friction alone. Either `friction_kinetic` is too high or `j_platform` too low, and those two are exactly what the breakaway-torque measurement would separate. The control law converges either way, but the settling curve is not yet evidence of anything about the real rig.
- **POINTING is written and its control law is unit-verified, and the loop then said something worth more than a passing scenario: this rig cannot observe its own pointing error.** Three runs, three distinct failures, none of them the control law's fault:
  - a **0.35 rad/s shove is completely invisible**. friction absorbs it in ~70 ms, so the gyro reads exactly zero at every 10 Hz sample while the platform quietly creeps 0.117 rad. the controller never commands anything because nothing ever moved as far as it can tell.
  - a **2.0 rad/s impulse aliases**. the disturbance happens mostly between samples, so integrating sampled rate gave a heading of 0.034 rad against a true 0.130 - the controller stopped correcting because it believed it was inside the band while it was 2.6x outside it.
  - a **sustained push saturates the wheel** at 36 rad/s in about a second, after which there is no authority at all and the error runs to 0.76 rad.
- **The band in REQ-ADCS-002 is a sensing limit on this bench, not a control limit**, and the requirement now says so rather than being marked verified against a disturbance chosen small enough to pass. Integrating rate to get heading is dead reckoning; it can only ever see what it samples, and at 10 Hz against friction this strong it samples almost none of a transient. Fixing it means measured parameters first, and probably an attitude update faster than the control cycle.
- **SIL-012 grades the one thing here that is genuinely true and reproducible** - that a sustained disturbance fills the wheel and pointing authority is lost. That is the case the eventual actuator fault exists for, and it is a better argument for adding one than any amount of asserting that saturation is bad.
- Worth being clear about what this cost and what it bought: a day of estimated parameters produced no settling curve for a resume, and three specific, defensible statements about what the hardware can and cannot do. **The second is the thing a plant model is actually for.**
- **The inertias are measured now, out of Fusion rather than off a scale.** Izz about the spin axis, converted from Fusion's g mm^2 by 1e-9: the flywheel as built (8 of 16 pockets filled with M4 steel) is **1.09e-4 kg m^2**, and the rotating stack less the wheel is **4.53e-3 kg m^2**. Fusion integrates the real geometry, so this beats weighing parts - a scale gives mass and leaves the radius distribution to guesswork, and inertia is mass times radius squared. The CAD's own gap is unmodelled connectors and wiring near the walls, which would push j_platform up, so it reads slightly low.
- **The estimates were wrong in the direction that matters.** j_wheel was 2.8x too high and j_platform 34% too low, and the two errors compound into the number that governs everything: **the wheel's entire momentum budget is 0.0039 kg m^2/s, which is 0.87 rad/s (50 deg/s) of platform rate.** The estimated parameters said 3.6 rad/s. Every manoeuvre on this rig has to fit inside four times less authority than yesterday's model implied. Filling the other eight bolt pockets buys ~30% more and is the cheapest authority available.
- **SIL-011 survives the new numbers, and only because of friction.** It starts at 2 rad/s, which is over twice what the wheel can hold; bearing drag takes it to ~1.2 rad/s in the 200 ms before DETUMBLE is commanded, and the wheel absorbs the rest at 76% of full. An immediate entry at 2 rad/s would saturate. That dependency is now written into the scenario rather than left as a passing test nobody looked at twice.
- **SIL-012 got better under real parameters.** With the wheel full, the console shows the controller commanding `WHEEL 50` - full torque - on every single cycle while the platform coasts down on friction alone and the heading runs to 3.7 rad. **A controller asking for everything and receiving nothing is what loss of authority actually looks like**, and it is a far stronger argument for the actuator fault than any assertion that saturation is bad.
- **Friction got measured too, with a stopwatch and no instruments at all.** Spin the platform by hand to roughly one revolution per second, time it to a stop: ~6.28 rad/s to rest in ~2 s, so ~3.1 rad/s^2 and ~0.014 N m of drag against the measured inertia. The guess had been 0.015 - right to within 7%, which is the useful kind of surprise. The model was still ~30% too draggy overall because its viscous term was doing too much work, and it now coasts down in 1.8-2.0 s against the measured 2.
- **One measurement cannot separate coulomb friction from viscous** - both decay, and only the *shape* tells them apart, which a hand-timed stopwatch cannot resolve. The split assumes coulomb-dominant, the right prior for a loaded ball bearing, and says so in the header. The gyro could log a real decay curve once the vehicle can be spun and left alone, and that would settle it properly.
- **Breakaway is still unmeasured and still the gap**, because a coast-down only ever sees the sliding case and never the sticking one. It is a guess (1.25x kinetic) sitting on top of a fit, and it is the number the pointing controller lives or dies by.
- **The fit made detumble harder, which is the point of fitting.** Less drag means less free help: the wheel now peaks at 34.3 of 36 rad/s to recover a 2 rad/s hand-spin, 95% of capacity against 76% before. **That makes ~2 rad/s about the largest upset this vehicle can recover from**, and it is a far more useful thing to know than a settling time.
- **Phase 8 started: SPI3 arbitration, then the LoRa driver.** The bus lock moved off the camera and onto the *peripheral*, because SPI3 carries the camera and both radios and a lock hanging off a device handle would let two of them think they each had the wires. The camera's own mutex is gone - it takes the SPI3 bus lock across every public call now, which serialises its state machine and the bus in one object.
- **The camera's FIFO burst no longer spans calls, and that is the change to watch.** It used to leave chip select asserted across chunk reads to save re-sending one command byte per 56 bytes. That is fine while the camera is alone on the bus and unacceptable the moment a radio shares it - a held CS means the camera gets clocked by traffic meant for something else. It closes per chunk now, under 2% overhead against a whole class of corruption. The ArduChip's read pointer should survive the deselect, since rewinding it takes an explicit `FIFO_RDPTR_RST` and that is exactly what `scan_jpeg_length` uses - **but that is reasoning, not evidence**, and REQ-PAY-003 carries a re-test note rather than pretending otherwise.
- **The RFM95 driver is written and brings up in the same shape as the camera**: hardware reset first (a warm MCU reset does not reset the radio, so without it the driver would be configuring a chip in whatever state it was left in), then read `REG_VERSION` and refuse to configure anything unless it reads 0x12. 915 MHz, SF7 for short air time on a bench, a private sync word so the link ignores every other LoRa device in range, and PA_BOOST rather than RFO - the RFM95 wires its antenna to PA_BOOST, and choosing RFO transmits into a disconnected pin and simply never works.
- A small thing worth remembering: the driver compiled and then **did not appear in the image at all**, because nothing called it and `--gc-sections` dropped the lot. `nm | grep rfm95` returning zero was the only sign. Same family as the glob problem - the build being green says less than it looks.
- **Both bench checks passed on one flash.** `LORA: up` - the radio answers with version 0x12 - and the payload downlink re-ran clean at 146 chunks and 8175 bytes with the image intact, so **closing the FIFO burst on every chunk was safe**. The ArduChip's read pointer does survive the deselect, which was reasoning before the run and evidence after it.
- **Telemetry goes out over LoRa now, and the air-time budget designed it.** One 21-byte heartbeat at SF7/BW125 is ~57 ms on the air. At 1 Hz that is 5.7% duty and comfortable; the full telemetry stream is about five frames per 100 ms cycle, which would want **2.8 seconds of air time per second of flight**. That is not a tuning problem, it is an impossible one - so the radio carries the heartbeat and nothing else, which is precisely the dual-link split the architecture asked for back in June. The frame is byte-identical on all three transports, which is the whole of REQ-TLM-004.
- **The beacon is one slot deep, not a queue.** A backlog of heartbeats would broadcast an ever-staler picture and never catch up at 57 ms a packet, so a newer frame replaces an untransmitted one and the replacement is counted. A beacon says what is true now.
- **The radio work happens in the telemetry task, never in the caller.** `rfm95_send` reaches for the SPI3 bus lock, which the payload downlink can be holding - and the control task must not block on a radio. Same argument that moved `uart_write` out of the control cycle two days ago, applied to a different resource.
- **The boot banner read `IMU gyro bias: -269 39 -31`**, where earlier runs read about -4 on that axis. Not a bug - the driver subtracts the boot bias on every read - but it is a warning: the bias comes from 64 samples taken at startup, so a rig that is moving then bakes that motion into the offset and over-corrects every later reading. On Z it was ~10 counts out, about 0.3 deg/s, which is nothing for detumble and **integrates into roughly 0.3 rad of phantom heading per minute in POINTING**. Boot now prints `IMU BIAS SUSPECT` past a plausibility threshold, because the failure is silent otherwise and lands on the one mode already known to be fragile about heading.
- **The nRF24 driver landed and the dual link is complete.** Payload chunks now go out over the high-rate radio from the downlink task, which is the traffic that radio exists for and the reason DOWNLINK is a mode rather than a label. The same encoded frame now leaves the vehicle over **two uarts and two radios** - four transports, one format, which is REQ-TLM-004 stated as plainly as it can be.
- **A 70-byte frame does not fit a 32-byte packet, and the frame did not shrink.** The driver splits and the receiver concatenates, because the frame decoder already resyncs on AA 55 and validates a CRC - so the radio is a byte pipe exactly like a uart, and a lost packet costs one frame to a CRC failure instead of desynchronising the link. Shrinking `kPayloadChunkBytes` to suit one radio would have made every other transport worse to accommodate the newest one, which is the opposite of what a swappable transport means.
- **Two nRF24 details that would each have cost an evening.** There is **no version register** on the part, so presence is proven by writing the five-byte transmit address and reading it back - five matching bytes is not something a floating bus produces. And **CE is held high** rather than pulsed: the usual pattern needs a 10 us pulse per packet and this project has no microsecond delay, but held high the part sits in standby-II and transmits whatever lands in the fifo. Same result, no timing to get wrong.
- **Auto-ack is off, deliberately.** Enhanced ShockBurst would retry every packet to its limit against a receiver that does not exist yet and stall the link doing it. One-way broadcast until the ground station is real, at which point acks become worth having and the decision gets made with something to test against.
- **The nRF24 came up on the bench too**, and the payload arc re-ran clean at 138 chunks / 7687 bytes with the image intact. `LORA: up` and `NRF24: up` both in the banner, all seven tasks healthy, no regression from adding a third and fourth transport.
- **The ground station started, and the Teensy is out.** The Feather M0 RFM95 replaces it: the radio is already on the board, SPI stays free for the nRF24 receiver, I2C is free for the display, and it is its own USB serial port. A Teensy would have meant wiring a second RFM95 to gain nothing.
- **The display choice was decided by voltage, not size.** The I2C 16x2 LCD backpacks are 5 V parts, and their I2C pull-ups would put 5 V on the Feather's 3.3 V pins - the same hazard class as the AS5600 note in `wiring.md`. The SSD1306 is natively 3.3 V, and 128x64 shows mode, faults, link and sequence at once where 2x16 characters cannot.
- **`gsw/` compiles `common/protocol/` rather than reimplementing it.** That was always the intent - `fsw/CMakeLists.txt` has said "shared with the ground box firmware when it lands" since June - and it means a wire-format change cannot silently desync the ground box the way a hand-written decoder would. Three consumers now, one definition.
- **The ground firmware is a byte pipe and that is the whole design.** A packet arrives, its bytes go out USB, and `uart_monitor.py` decodes them with the FrameDecoder it already uses on the ST-Link cable. It parses nothing. That only works because the frame format does not change per transport, which is the property REQ-TLM-004 exists to protect - the ground station is the first thing to actually cash it in.
- The one thing it does decode is whether a frame passed CRC, and only to blink the LED, so the box says something with no PC attached. Even that runs the satellite's own `frame.cpp`.
- **Every modem setting is copied from `obc/Src/devices/rfm95.c` deliberately**, with a comment saying so: a mismatch between the two ends does not produce an error, it produces silence, which is a far more expensive thing to debug.
- **The vehicle was heard over the air**, and it took a bug fix to get there. The beacon never transmitted once: `service_beacon` gated on `rfm95_tx_done()`, and that read the TX_DONE interrupt flag - which is **zero on a radio that has never transmitted**. So the first send waited for the completion of a transmit that only that same check could have started. A deadlock that a build cannot catch and only a bench can. Fixed with an explicit in-flight flag; `HEARTBEAT` now decodes at 1 Hz off the Feather with no ground-side change at all.
- **Ctrl-C did not work in `--read-only`**, which is a Windows detail worth remembering: an untimed `Event.wait()` blocks inside the C layer and never returns to Python to run the signal handler. Polling with a timeout fixes it.
- **The console and the ground console were always the same program.** `obc-monitor` is `uart_monitor.py` with `--stlink`; there is no second tool. What was missing was the matching convenience for the Feather, so `gsw-monitor` now pins its port by USB vendor id - the ground station's serial number is per-board and cannot be committed, its vendor id can.

### 2026-07-31 - the ground box grows a second radio and a face

- **The nRF24 receiver forced a protocol decision the satellite had dodged.** The vehicle was writing variable-length packets - 32, 32, then 6 for a 70-byte frame - and a static-payload-width receiver has to know the size in advance. The alternative, dynamic payload length, **requires auto-ack**, which is deliberately off so the vehicle never stalls transmitting at a ground station that might not be listening.
- **Resolved by padding to a fixed 32 on the satellite**, which works only because of a property built in months ago: the frame decoder resyncs on AA 55 and validates a CRC, so trailing zeros between frames are skipped exactly like line noise on a uart. 96 bytes of air per 70-byte frame, 37% overhead, and at 1 Mbps not worth a second thought. **The decoder being resilient is what made the cheap answer the right one.**
- **Both radio streams share one USB port on purpose.** Same frame format, one decoder, and the ground tooling already reassembles payload chunks out of a single byte stream - so beacons and image chunks interleaving costs nothing and needs no demultiplexing at either end.
- **The display is the only thing in the ground station that reads a message**, and it uses the satellite's own `state.hpp` catalogs to name modes and faults. A fault renamed on the vehicle renames on the screen at the next build rather than quietly showing the wrong word. It also distinguishes inhibited faults from acting ones, because the satellite draws that line and a readout that flattened it would be lying.
- **One radio down is not a dead ground station.** Only both failing is a hard stop; a single working link still hears the vehicle, and saying which one failed is more useful than refusing to run.
- gsw builds at 29740 flash / 4776 RAM on a 256 KB / 32 KB part - the SSD1306 framebuffer is 1 KB of that and there is room to spare.

### 2026-07-31 - the legacy sweep

- **The radios had no telemetry at all.** Every other subsystem reports whether it is alive; the two newest did not, so a dead radio was invisible - no fault, no status, nothing. `msg.hpp` had `LoraStatus` and `Nrf24Status` reserved since June and never filled in. Both are live now, one `radio_status_t` shape for both because the question is the same: configured, still answering, how much carried, how much refused.
- That also gave four orphaned functions and two dead counters a purpose. `rfm95_alive`, `nrf24_alive`, `nrf24_dropped` and the beacon's replaced-frame count were all written and never called - **which read like dead code and was actually a half-built feature.** Deleting them would have been the wrong call.
- **Deliberately no radio fault.** What a spacecraft should *do* about a dead beacon is a real decision, and this project's own rule is that a fault nothing responds to is just a catalog entry. Observability first; the response when there is something to respond with.
- **Radio status goes out the wired links only.** A dead radio cannot report that it is dead, so putting its health on itself would be theatre.
- **`ov2640_discard` has no caller and should not get one.** That was on the audit list as a gap and the audit was wrong: a captured frame has to survive between contact passes for a downlink to be resumable (REQ-PAY-004), so nothing autonomous may bin it, and starting a new capture already flushes the fifo. It wants a ground command, not an internal caller - which is now said in the header instead of left looking like an oversight.
- **The IMU takes the SPI2 bus lock now**, though spi2 carries only the imu and the lock is uncontended. Both buses obey one rule: an exception that holds because "nothing else is on this bus yet" is an exception that stops holding silently, and spi3 already taught that lesson.
- Also gone: `ov2640_lock_init` (an empty function kept for symmetry after the camera moved to the bus lock), the ESC's `[env:probe]` build from June, and the four tracked CubeIDE project files - CMake has owned the obc build since 07-29 and `.cproject`/`.project`/`.settings`/`obc.launch` were the pre-migration remains.
- **Left alone deliberately:** the `TEMP esc rx:` block in `control_task.cpp`. `roadmap.md` says delete it when the ESC link works, and the ESC still is not connected - that is owed work, not legacy.
- **Bench-confirmed, and it caught the health task drifting under the stack floor for the second time in two days.** Both radios report `up`, `LORA sent` climbs exactly 1 per second - one beacon per heartbeat - and `dropped` stays 0, so the one-slot beacon is never being outrun. But health went from 168 words free to 137: emitting two radio-status frames costs another payload and frame buffer on that stack, taking it from 98 words used to 119 and from 2.6x margin back down to 2.15x. Raised to 320.
- That is the same task, the same failure, one session after writing "every task that gains work needs re-measuring, and nothing prompts you to do it". **It is not a lesson that stays learned by being written down** - the number sits in every TASKS line until somebody reads it, and the only reason it was caught this time is that the line was read.
- Verified: 45/45 unit (826 assertions), 144/144 pytest, 12/12 SIL, trace current, obc links at 51588 text, all four builds green.

### 2026-07-30 - the camera dropout test, and a four-day wiring mystery closed

- **REQ-PAY-002 was meant to be a ten-minute demonstration and turned into the root cause of a July debug.** Pulling the camera's SPI3 harness on a live board raised `CAMERA_DROPOUT` as designed - and also `POWER_DROPOUT`, with `I2C scan` returning **0x48 alone**. Both the camera at 0x30 and the INA228 at 0x40 had left the bus. That is the same pairing as the 2026-07-26 connector incident, where replacing one cable brought back two devices and the entry recorded the mechanism as "not fully explained".
- **My first hypothesis was wrong and the measurement is what killed it.** I reasoned from the datasheets - TMP117 runs down to 1.8 V, INA228 needs 2.7 V - and predicted a 3.3 V rail droop that would take out the INA while the TMP survived. A multimeter across every VIN/GND pair read a clean 3.3 V. No droop. **The asymmetry was real and my explanation for it was invented**, which is the failure mode of reasoning from a plausible story rather than a probe.
- **The actual cause came from the one reading that did not fit: the camera measured ~500 mV.** Its 3V3 arrives on the power/SCCB run and its GND arrived only on connector 3, so unplugging that connector left it **powered but ungrounded** - floating, and still tied to the shared I2C1 bus through its SCCB pins, which it then uses to hunt for a return. On a bus already marginal at ~286 pF and 600-1000 ns rise times, that parasitic load is enough to push one device off. Which device survives is a coin flip of input thresholds, not a fact about the INA.
- **`wiring.md` had already predicted this in the abstract**, in the connection-order note: a chip with no valid ground reference finds its way out "through whatever pins *are* at a defined potential - typically the I2C lines". Written as general caution, and then not applied when a device was wired with power and ground on separate connectors. **A rule stated in a document is not a rule applied to a build** - the gap was never knowledge, it was that nothing checks a harness against the guidance in the same file.
- **The fix was one wire: ground on the camera's power run as well as on connector 3.** The retest is unambiguous - `I2C scan: 0x30 0x40 0x48`, every device acking with the SPI3 harness still out, `POWER_DROPOUT` gone, only `CAMERA_DROPOUT` raised. **0x30 answering is the part that proves it**: a healthy SCCB side means the camera is properly referenced, so the surviving `CAMERA INIT FAIL` is the ArduChip genuinely absent over SPI3 rather than a chip dragging its neighbours down. Reconnecting and resetting came up fully clean. Both grounds stay - every connector carrying signals wants a return path, and two means no single unplug can float the device.

### 2026-07-30 - telemetry and payload get their own tasks, and the last leaked constant goes home

- **The telemetry task owns both output uarts now.** `uart_write` spins on `__WFI` when its 256-byte tx ring fills, and a DOWNLINK cycle offers ~390 bytes per link - so the stall was landing in the control task, the highest priority in the system and the one place a stall means a late control response. The blocking did not go away; it moved to priority 3, where the rest of the system runs through it. Producers now enqueue into a 1 KB stream buffer and return.
- **Enqueue is all-or-nothing, and that is the whole correctness argument.** `xStreamBufferSend` will accept a partial message, and half a frame spliced into a byte stream leaves the ground resyncing on garbage - so it checks space first and drops whole messages, counted and printed as `TLM DROPPED n`. A telemetry path that can lose data silently is the one thing this project does not accept.
- **A bug I wrote and clang-format exposed:** the pre-scheduler path inferred which uart to write from which buffer handle it was given, but before `telemetry_task_create` runs *both* handles are null, so the test answered the same for both and the entire boot banner would have gone out the downlink header instead of the console. Passing the uart explicitly is the fix. Worth noting how it surfaced - reformatting put the two lines next to each other and the tautology became visible.
- **`console_printf` locks across the format.** `configUSE_NEWLIB_REENTRANT` is 0, so there is one copy of newlib's state for the whole system; the config comment has promised this since the kernel landed and now three tasks can print.
- **The payload downlink is its own task, and `kPayloadChunksPerCycle` is gone.** Four-chunks-per-cycle was never a flight-software fact - it was a uart ring size divided by a frame size, a link property that had leaked across the PAL and would have been wrong the moment the radio ran at a different rate. The executive now calls `set_payload_downlink(mode == DOWNLINK)` and the task paces itself by filling the output buffers and waiting for them to drain. The rate comes out as whatever the wire carries, with no constant to be wrong.
- **Sending a level rather than an edge is what makes safing free.** Because the flag is recomputed every cycle from the mode, a retreat out of DOWNLINK stops the stream with no hook of its own - and there is a unit test that asserts exactly that, since it is the kind of property that quietly stops holding.
- **The camera mutex went on the driver's api, not on the spi bus**, which was my first instinct and wrong: `ov2640_read_chunk` leaves CS asserted *across calls* for a burst read, so a lock inside `spi_select`/`spi_deselect` would be held between calls and released by whichever task happened to close the burst. The real shared resource is the driver's state machine, and the bus transaction is a part of it. Recorded a phase-8 note in the same place: when the radios join SPI3, whatever arbitrates the bus has to make the camera close its burst before yielding, because a held CS would let the radios clock the camera.
- **The glob bit for the third time.** `file(GLOB_RECURSE)` is evaluated at configure time, so adding `downlink_task.cpp` and rebuilding linked the old file list and the symbol came out undefined - which the linker reports as "dangerous relocation: unsupported relocation", not as anything resembling a missing file. `CONFIGURE_DEPENDS` on both globs makes it structurally impossible now. Three sessions lost to the same class of failure is two too many.
- **The SIL runner would have died on `WHEEL` and `CAPTURE` too.** It parses shim output strictly and dies on an unrecognised tag; adding `PAYLOAD` revealed that two existing action lines had simply never been triggered by a scenario. All three are recognised now and recorded as gradeable events, so a scenario can check dispatch and not only state.
- **Bench-verified, and the run found a watchdog bug.** Seven tasks reporting, the full arc walked (`DETUMBLE -> POINTING -> CAPTURE_IMAGE -> DOWNLINK`), 110 chunks reassembled to a 6117-byte `JPEG OK`, and no `TLM DROPPED` at any point - the self-pacing held. **The whole image went out inside a single second**, against about three seconds on the old four-chunks-per-cycle path, which is the constant's removal showing up as throughput.
- **`WATCHDOG UNFED` appeared once, mid-downlink, and it was a real defect rather than a noisy report.** The downlink task checked in only after its fill loop, and that loop does not fill-and-exit the way I wrote it to: the telemetry task drains the buffers while this one fills them, so room keeps reappearing and the loop runs until the whole image is gone. It sat there 604 ms against a 500 ms deadline, so the health task correctly judged it hung and refused to pet the dog.
- **That would have reset the board on a bigger frame.** The IWDG is 3000 ms and the health task pets at 1 Hz, so one missed pet is survivable - which is why this presented as a warning. A full-resolution JPEG is 30-60 KB, several seconds in that loop, three or more consecutive missed pets, and a reset in the middle of a downlink. **A latent reset found by a warning that was easy to wave off**, on the first run where the frame was small enough to survive it.
- **The fix is where the check-in goes, not how long the loop runs.** The task was never hung; it was doing exactly its job. A pass here has no bounded duration by design, so liveness is now reported per chunk. Bounding the loop instead would have meant reintroducing a chunks-per-pass constant - the very thing this change deleted. It still goes quiet if `send_chunk` itself wedges, which is the case the deadline exists for.
- The general lesson, and the second time this project has hit it: **`task_health_checkin` at the end of a loop body assumes the loop body is short.** The existing rule in `task_health.hpp` says to check in at the end of a pass rather than the start, which is right - but it says nothing about a pass whose length is set by how much data exists.

### 2026-07-30 - 42 set aside, and the uplink moves off the control task

- **NASA 42 evaluated and dropped.** The full reasoning is in `roadmap.md` under Simulation, but the deciding argument: 42's value is environment fidelity - geomagnetic field, gravity harmonics, drag, solar pressure - and a lazy susan has none of that. **It does not model the one thing that will dominate the rig's behaviour, which is stiction in a cheap turntable bearing**, and that has to go into the plant model either way. - **The uplink is its own task now.** The control task used to drain both uarts every cycle, which was wrong twice over: it polled a link that is silent almost always, and `fsw::Inputs` carries one command, so a burst arriving inside one 100 ms cycle kept only the last and dropped the rest silently. That limitation was commented rather than fixed, on the grounds that every command is acked and the ground would resend - true, and still a worse answer than not dropping them.
- **The rx isr now notifies a waiter** (`uart_set_rx_waiter`), which is this project's first `FromISR` call - and the reason the other agent's explicit NVIC priorities had to land first, since a FromISR caller must sit at or below `configMAX_SYSCALL_INTERRUPT_PRIORITY`. The one-producer/one-consumer rule on the rx ring is unchanged: the isr still only fills, one task still only drains, and the notification carries no data.
- Two decisions worth their comments: the task **times out at 200 ms even with nothing arriving**, because a task that only checks in when the ground talks looks hung to the watchdog on any bench without a ground station; and a **full queue drops rather than blocks**, because blocking there would stall both uplinks behind one slow consumer, and a dropped command is already handled - no ack, ground resends.
- **This is one of three, and stopping here is deliberate.** The telemetry task (which takes ownership of all console output, since `configUSE_NEWLIB_REENTRANT` is 0) and the payload downlink task with the SPI3 mutex follow the same shape. Changing one concurrency boundary at a time is what makes a bench failure attributable; changing three at once is how you spend an evening bisecting your own diff.
- **Bench-verified.** Five commands piped back to back - all five `SENT` lines out before any reply - came back with five acks, seq 1 through 5, delivered about one per control cycle as the queue drained. On the old path they would have landed inside one or two cycles and only the last of each would have been acked. The rejection among them (a DETUMBLE self-transition) is an ack too, which is the point: every command is answered.
- **The task's stack was resized off its own measurement.** Idle it peaked near 40 words of 192, but decoding one command took it to 113 - `frame_decode` returns `std::optional<frame_t>` by value and that carries the 64-byte payload buffer, which at -O0 lands on the stack whole. That left 79 words free, the tightest margin in the system, on the one figure this project already documents as reading optimistic. Now 320 words, ~2.8x the measured peak and matching control's ratio; the peak reproduced at exactly 113 on the second run, so it is a real number rather than a fluke. Cost: 512 bytes of bss out of 128 KB.
- A reading that looks broken and is not: the uplink's check-in age pins to a constant. The task wakes every 200 ms and the health task samples every 1000, so the two are harmonically locked and health always catches it at the same point in its cycle. Benign, but it means that particular age is never a representative sample.

### 2026-07-29 - the watchdog bites, and phase 6 has its evidence
- **IWDG on the lsi, serviced only on evidence.** The health task pets it exclusively when every task registered with a liveness deadline has checked in inside it - control and sensors at 500 ms, five missed cycles each. Health and idle register a deadline of 0 and are reported but not judged: judging the reporter is circular, since a health task that stops running stops petting anyway. Petting from a timer or an isr would have proved the interrupt still fires, not that the software still works.
- **The lsi is an rc oscillator, 17-47 khz, so the period cannot be exact.** The reload is sized against the *fast* end, making the requested timeout a guaranteed floor rather than a target - ask for 3 s, get at least 3 s and up to ~8 s on a slow part. Erring long is the safe direction: a watchdog that bites early resets a healthy board. Also learned the hard way from the reference manual: `PR` and `RLR` live in the lsi clock domain, and writing one while the previous write is still pending is silently ignored, which would leave the default period in place. The driver waits on `PVU`/`RVU`.
- **Bench-verified by removing the control task's check-in.** Console showed `control: blk 331w` with no check-in age at all (the never-checked-in sentinel) and `WATCHDOG UNFED` for four consecutive seconds, then the board reset and came back with **`BOOT: reset=iwdg-watchdog`**. REQ-WDG-001 and REQ-WDG-002's watchdog case both closed in one run. The withheld pet being visible in telemetry *before* the reset is what makes the reset attributable instead of mysterious.
- **The same log exposed a false alarm worth fixing.** The health task is the highest-priority periodic task, so on its very first pass it ran before any lower-priority task had checked in even once, judged them stale, and printed `WATCHDOG UNFED` on a perfectly healthy boot. Now it waits a period before its first report. One spurious "about to reset" line per boot is exactly how a warning gets trained into background noise - the same reasoning that keeps inhibited faults off the led fault ladder.
- **Deliberately not added: a ground command to stop petting.** Convenient for the demo, but it would put a self-destruct in the wire contract permanently to serve a one-time demonstration. Commenting out a check-in and flashing is the honest way to test it.
- **HIL-003, the scheduler-smoke scenario phase 6 owes**, and the harness grew three expectations to grade it: `tasks_reported` (an exact set, so a task that silently stops being created fails), `watchdog: fed` (no report may have withheld the pet), and `stack_free_min` (a floor, not a measurement - the stacks were sized at 4-5x the observed peak, so dipping under 64 free words means a task's work grew and the sizing needs redoing). The WHEEL_DROPOUT retreat stays unit-only deliberately - a third scenario would restate SIL-009 with one name changed.

### 2026-07-29 - task health on the wire, and the first mutex the project has needed
- **Symmetric task files first.** `control_task.cpp` now owns the cycle, the led policy, and the bench inhibits (which belong next to the banner that reports them), and `console.cpp` owns the console helpers now that bring-up and the control task both need them. `main.cpp` is board bring-up, three create calls, and `vTaskStartScheduler()`. Bss byte-identical, text +48 - a pure move.
- **`MsgId::TaskHealth` (0x30), a new block for health of the *computer* rather than the spacecraft.** Each task calls `task_health_checkin()` at the **end** of its loop body, not the start - a task that wakes and then hangs mid-pass has not done its job, and only an end-of-pass check-in catches that. The health task reads every slot, adds `uxTaskGetStackHighWaterMark` and `eTaskGetState`, and sends one 47-byte snapshot at 1 Hz. Fixed-size struct sized for the whole planned task set plus idle, so adding a task does not change the wire layout.
- **The report is assembled by the platform, never by the fsw.** Task health is not flight-software state, and routing it through the executive would mean the fsw learning that tasks exist - which is the one thing that would break `Executive::cycle()` being identical between SIL and the target. It goes out the same way `send_payload_chunk` does: build the struct, `frame_encode`, write both links.
- **The idle task is in the report and it is the one worth watching** - 128 words is the smallest stack in the build. Its handle only exists after `vTaskStartScheduler()` creates it, so the health task registers it on its own first pass rather than from a create function (`INCLUDE_xTaskGetIdleTaskHandle` had to go on).
- **Adding the health task created a real data race, and fixing it is the project's first mutex.** Two tasks now write `uart_console`, and `uart_write` was never reentrant: it reads `tx_head`, waits for room, then stores - preempt it mid-write and two frames interleave into one unreadable stream. So each uart got a static tx mutex. This is exactly the distinction from the concurrency decision: the uart is a shared **resource**, like the i2c bus, and mutexes are for those and never for shared flight state. Details that matter: the lock is conditional on the scheduler running, since bring-up writes before it exists; it is held across the wait-for-room spin on purpose, because a frame half in the ring is not a frame; and freertos priority inheritance bounds the block, so the control task waiting on a lower-priority writer boosts it rather than waiting behind it.

### 2026-07-29 - the scheduler is in the image: control and sensors are tasks now
- **Phase 6 opened with the prerequisite, not the feature.** `uart.c` set no interrupt priority at all, so all three uart isrs ran at the reset default of 0 - the one value from which a `FromISR` call is never legal. So the driver keeps the vector, and `systick_kernel_tick_enable()` (called immediately before `vTaskStartScheduler`) makes each tick also forward to `xPortSysTickHandler`. The port programs the same 1 ms period, so `millis()` counts ms without a discontinuity across the scheduler start. The forward is declared `extern` in systick.c rather than by including the kernel headers - the port declares it privately in port.c, and the driver has no other business with them.

The i2c and spi reads block on peripheral flags for every byte, which is exactly the work a fixed-rate loop must not carry; now they stall a lower-priority task and the control cycle takes whatever was last published. A device that failed init still publishes its default (invalid) sample, so `SENSOR`-side dropouts detect the same as before. On a cycle with nothing new the three samples stay **unset**, which the monitor already treats as "not offered" - a silent sensor task is a task-liveness question for the watchdog, not a sensor fault.

What actually happens: `millis()` is sampled *after* `read_sensors()`, so `scan_jpeg_length()` inside `ov2640_poll()` - a byte-by-byte scan of the whole ~8-10 KB fifo over polled spi - pushes that one cycle's **timestamp** ~16 ms late, well inside the 100 ms budget. `heartbeat_due()` then fires on the first cycle past 1000 ms and re-anchors on the *actual* fire time, so a 16 ms nudge made the next fire miss its cycle by 16 ms and land on the following one, 100 ms later, where it locked. - **BOOT was a dead end and nobody had noticed.** Nothing ever requested BOOT -> STANDBY. The transition was legal in the table but no code path asked for it, so the only exits were a ground command or a fault safing the vehicle - and COMMAND_LINK_LOSS safing at ~5 s had been hiding it since the mode manager was written. Inhibiting that response is what exposed it. Now **REQ-MODE-010**: leave BOOT on the Nominal trigger once every detector has had a full debounce window (3 cycles, matching the longest debounce) and nothing Critical latched. Hopping out on cycle one would declare the self-check passed before a persistently bad sensor could possibly have failed it. Confirmed on the bench - heartbeat seq=0 BOOT, seq=1 STANDBY.
- **The fault bead grew a rung below Warning.** Ladder is now red Critical / orange Degraded / yellow Warning / **dim blue inhibited** / off clean, worst rung wins. An inhibited fault is kept out of the three alarm rungs entirely: it stays in the heartbeat and the boot banner, but a bench build routinely runs with subsystems absent and letting those hold the bead red every boot is how a red indicator stops carrying information. Dimmer as well as a different hue, so it reads as status not alarm. The link bead now tests `response_active()` too, which makes it fall through to **amber - never acquired**, the truthful state on a bench with no ground station, rather than red.
- Severity ordering (Warning < Degraded < Critical) is now pinned by a `static_assert` - the safing mask and the led ladder both compare with `<`, so reordering the enum would silently reorder both. It was already correct; it just was not guaranteed.
- Verified: 36/36 unit, 62/62 pytest, 8/8 SIL, obc at 28376 text.

### 2026-07-27 - a real 7688-byte jpeg out of the camera, and fault inhibits
- **The camera produced a frame.** Two bugs found by comparing against arducam's reference sequence rather than reasoning from the register map, which is the third time this week that reading the source beat thinking about it.
  - **Missing `0xff/0x01` then `0x15/0x00`** between the jpeg tables and the size table. 0x15 is COM10 in the sensor bank - vsync/href polarity, the signals the arduchip latches frames on. Without it every table writes with no nack and no frame is ever delivered, which is exactly what `state=3` was.
  - **Wrong fifo write.** Was clearing with `CLEAR|RDPTR_RST|WRPTR_RST` in one go; upstream never touches the pointer-reset bits in the capture path and instead issues a bare `CLEAR` **twice** (flush, then clear-done-flag) before `START`. The two identical writes are not redundant - the second is what stops a stale done flag reading as an instant completion.
- **Then the bench answered the last open question by itself.** First good capture returned 7688 bytes with `head=D8 FF E1 01` - a valid jpeg missing exactly one leading byte, `FF E1` being the exif APP1 marker sitting right where it belongs. So the burst read has **no dummy byte** after the command; discarding one was eating the `FF` of the SOI. Removed, and the comment now records that this was measured, not assumed. The bring-up block also now drains the **whole** frame in 64-byte chunks and checks SOI and EOI, since a good opening marker alone would not prove the read pointer survives across calls.
- **Fault-response inhibits (REQ-FAULT-012).** The bench is routinely missing subsystems the flight configuration assumes: no ground station means COMMAND_LINK_LOSS safes the rig ~5 s after every boot, and the esc is physically out of the stack so WHEEL_DROPOUT latches on top of it. An inhibited fault still debounces, latches, logs, and appears in the heartbeat - **only the mode change is suppressed**. That split is the whole point, and it is what real commissioning inhibits do. The inhibit list is compile-time in `main.cpp` at the platform boundary (ground-commandable inhibits want a ground station, so phase 8), and the boot banner prints it, so a log with inhibits in force can never be read as a clean run. `Executive::inhibit_fault()` is the only writable door into the fault manager and cannot set, clear, or hide anything.

### 2026-07-27 - WHEEL_DROPOUT wired through the fsw, with an acquisition grace
- **The fault the esc link was missing.** `WHEEL_DROPOUT` has been in the catalogue (Degraded, debounce 3, REQ-FAULT-005) since the fault table was written but nothing ever raised it. It now runs end to end: `Inputs` carries an optional `wheel_status_t` set only on the cycles a frame actually lands, `SensorMonitor::evaluate_wheel` times the silence, and the executive retreats POINTING/DETUMBLE to STANDBY when it latches - a torque command into a dead link is a false claim of control.
- **The detector is the odd one out and the comment says so.** Every other detector reads a sample each cycle, so a missing one is no opinion. The wheel talks on its own schedule, so silence *is* the measurement and an arriving frame only resets the clock. The status flags (`FocReady`, `SensorOk`, ...) say whether the wheel can be *driven*, which is a separate question from whether the link is up; deliberately not folded in.
- **Two windows, not one.** Steady state is 1 s - the esc beacons every 250 ms, so four missed in a row is a dead link, and with the debounce that latches about 1.3 s after the last frame. The *first* frame gets 8 s, because the esc aligns foc for ~5 s from cold and says nothing until it finishes. Without that grace every single boot would latch a dropout that clears itself a moment later, which is exactly how a real fault gets trained into background noise. An esc that never comes up still latches once the grace expires, so the failure being chased this week stays visible. Deliberately *not* the COMMAND_LINK_LOSS pattern, where never-acquired and lost are indistinguishable - that one is already carried as an open observability problem, and repeating it was not worth the consistency.
- The 8 s grace also happens to be longer than the longest SIL timeline (t=5400), so all eight scenarios pass untouched. The shim never feeds a wheel status, so a shorter window would have forced WHEEL_DROPOUT into every scenario's expected fault set - noise in eight files that verify something else.
- Verified: 31/31 unit cases (four new detector subcases, two new executive subcases covering the retreat and the latch-only case outside the actuating modes), 62/62 pytest, 8/8 SIL, and the obc image builds clean. `docs/requirements.md` gained the WHEEL_DROPOUT fallback row and the detection rationale; REQ-FAULT-005's status now reads that this retreat is unit-verified while the other two still owe their scenarios.

### 2026-07-26 - ws2812 status array lit: pwm+dma transport, and a 3.3 V supply that was never going to work
- **New `pwm_dma` driver (tim1_ch1 + dma2 stream 1 ch 6, pa8).** A ws2812 has no clock line - the pulse *width* is the bit - so the cpu cannot be trusted to hit 400 ns targets 72 times without a single interrupt landing mid-frame. dma feeding `CCR1` once per period makes the timing hardware-exact. Worth being clear that this is **correctness, not optimisation**: i2c/spi/uart are self-clocked, so cpu lateness there is a harmless delay, which is why their dma work stays parked for phase 6.
- **Brought up in two scoped stages**, which paid for itself. Stage 1 (plain pwm, static duty) gave a clean 1.25 us / 50 % square wave and proved clock tree, af1 mapping, `BDTR.MOE`, and the preload/`UG` sequence in one trace. Stage 2 (dma feeding ccr1) then measured **0.4 us / 0.8 us highs on a 1.25 us period** - exact. Debugging one half at a time meant no trace was ever ambiguous.
- **Scope lesson:** auto-measure lies on a deliberately non-uniform waveform. It reported 1.65 us period / 48.5 % duty - and 48.5 % is just the mean of the real 32 % and 64 % duties. Cursors on individual edges are the only honest read here.
- **`ws2812` device driver on top** - framebuffer, **grb** byte order, msb-first bit encoding, latch tail, `pwm_dma_send()`. Kept register-free: it includes only `board.h` and `pwm_dma.h`, never `stm32f446xx.h`, which is the check that the device/driver split is real. Timing constants live in the *device*, so the transport stays generic.
- **The beads were dead for two stacked reasons, neither of them firmware.** First, the LED protoboard's **3V3 and GND rails were never bridged to the bead pads** - the data chain was soldered but the power bus was not, so continuity ran to DIN and nowhere else. Second, and the real trap: these beads are spec'd **3.5-5.3 V**, so the planned **3.3 V supply is below minimum** and they never light regardless. Moved the supply to **+5V on CN7-18**, kept 3.3 V data (no level shifter needed - that is how the Cyberbrick kit runs them), and all three lit immediately.
- **Latch tail raised 40 -> 224 slots (~280 us).** The old 50 us figure is the original ws2812 spec; the newer v5 beads want far more, and too short a latch means the frame never commits.
- Orientation confirmed by the bring-up colors: **bead 0 is the one nearest the data connector** = MODE, then FAULT, then LINK. Red reading as red (not green) is also the proof the grb order is right - that is the first thing that breaks.
- `main.cpp` swept: pwm scope scaffolding removed, a stale `// ...` dropped, and the boot **i2c scan promoted from TEMP to permanent** - an address-only scan at boot is exactly the diagnostic that would have cut short the "dead INA228" hunt, and it costs one pass at startup. The two camera blocks stay TEMP pending `ov2640.c`.
- **Mode/fault/link mapping landed (REQ-HMI-001).** Lives in `main.cpp` at the bsp/fsw boundary, so the fsw never learns an led exists and the driver only takes colors. Bead 0 = mode by color, bead 1 = the **worst** severity among latched faults (walks the fault table, so new faults need no new led code), bead 2 = uplink.
- **Link bead needed three states, not two.** Green-unless-latched was quietly dishonest: before the first command has *ever* arrived, an un-latched COMMAND_LINK_LOSS only means the dead-man timer has not expired yet - that is "unknown", not "good". Now **amber** = never acquired (the command log is still empty), green = in contact, red = lost - green/amber/red on one bead reads without a legend, where blue looked like another flavour of nominal, and off would be indistinguishable from a dead bead. Same never-report-unknown-as-healthy discipline the fault catalog already follows.

### 2026-06-06 - second UART (USART6) for a scope-able telemetry downlink
- Refactored `bsp` `uart.c` from a single hardcoded USART2 into a **handle-based driver**: a `uart_t` per instance (register block + its own ring buffers + error counts), a shared init core (`uart_start`) and a shared ISR body, with two named handles - **`uart_vcp` (USART2, PA2/PA3, AF7)** and **`uart_telem` (USART6, PC6/PC7, AF8)**. Added `clock_pclk2_hz()` since USART6 lives on APB2, not APB1. Telemetry now **dual-sends** every heartbeat/link-status frame to both.
- Why: USART2/PA2/PA3 is the ST-LINK VCP and is **isolated from the morpho/Arduino headers by default** (UM1724: SB13/SB14 ON, SB62/SB63 OFF), so it can't be probed on a header pin - found the hard way at the bench (clean frames on COM3, dead-floating on every header post). USART6 on PC6/PC7 is a plain header GPIO, so it's the scope / logic-analyzer-friendly downlink and the natural stand-in for the later LoRa (SPI) transport. `uart_vcp` stays the debug console.
- Bench-verified (Siglent SDS804X HD): scoped PC6, triggered the once-a-second burst (Single, falling edge), set up UART decode (115200 8N1, LSB-first, idle-high), and read a heartbeat frame off the wire by hand - `AA 55 01 0B ...uptime/seq... 34 40`, matching the host decode (uptime/1000 == seq). First real scope + serial-decode artifact for Phase 1.
